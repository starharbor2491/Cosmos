# Moving the engine to CEF

Cosmos ran headless Chromium snapshots and showed each page as a stream of JPEG frames. This note records why it moved to CEF (the Chromium Embedded Framework), what a prototype established, what the port found, and what is still to do.

## Why

- Google publishes no stable-branch Chromium for Mac. Snapshots are untested builds of the main branch, and Cosmos took a new one almost daily. CEF's own builds (cef-builds.spotifycdn.com) are cut from Chromium's stable branch.
- Headless Chromium can only be shown as screencast frames, with every click and key sent back over the DevTools protocol. CEF runs Chromium inside Cosmos, drawing into an `NSView` Cosmos owns.

## What the prototype established

CEF 156.0.14 (Chromium 156.0.8078.48), the minimal macOS arm64 build (134.9 MB, SHA-1 `7359a9d293dd5c480bec3f18b762731b483b0e13`), with a browser made inside an `NSView` of a window that was never shown:

- **Alloy style, always.** CEF makes a browser inside a view Cosmos provides an Alloy-style browser on macOS (`cef_types_mac.h`, `runtime_style`: "Alloy style will always be used ... if |parent_view| is provided"). Chrome style needs CEF's own Views windows.
- **The DevTools protocol still works, in-process.** With `--remote-debugging-pipe`, Chromium reads commands from descriptor 3 and answers on 4 of its browser process, which is now Cosmos. Cosmos sets up those descriptors before `CefInitialize`. `Browser.getVersion`, `Target.getTargets` (the CEF browser is an ordinary `page` target with a `browserContextId`) and `Extensions.loadUnpacked` (with `--enable-unsafe-extension-debugging`) all answered. The page agent, isolated worlds, request interception and permission code can stay.
- **Extensions mostly run.** In an Alloy-style browser an MV3 extension's content script ran at document start. Its service worker answered `runtime.sendMessage`, `sender.tab` carried an ID, and its `declarativeNetRequest` rule blocked a request, so Cosmos's blocker keeps working. `chrome.tabs.query({})` found **no tabs**, because Alloy browsers are not in Chrome's tab strip. The extension shim has to answer the tabs API from Cosmos's own tabs.
- `--disable-blink-features=AutomationControlled` keeps `navigator.webdriver` false under the pipe. The user agent has no "HeadlessChrome". Workers run.
- **No H.264** (`MediaSource.isTypeSupported('video/mp4; codecs="avc1.42E01E"')` is false). Standard CEF builds have no proprietary codecs and no Widevine, like the snapshots.
- `Extensions.loadUnpacked` has no profile parameter at Chromium 156 (`Extensions.pdl`), so it loads into the default profile. How to load per profile is still open.

## What changes for the user

- Pages are drawn by Chromium itself: real scrolling, text, colour, input methods and gestures, with no frame stream.
- One Chromium for all profiles (each profile a CEF request context with its own folder), instead of one Chromium process tree per profile.
- One engine version at a time, CEF's stable one. CEF's Stable API is ABI-compatible back and forward across a supported range of builds ("API versioning", since M133). Cosmos built against one `CEF_API_VERSION` can therefore load a newer CEF stable framework without being rebuilt, as long as that API version is still supported. Behaviour is not guaranteed, so each new build has to pass the live tests. That keeps Chromium's security fixes arriving between Cosmos releases.
- **Chrome's own password manager and autofill are Chrome-style features**, not available to Alloy-style browsers. Cosmos's password manager has to be Cosmos's own (macOS Keychain), with a switch in Settings.

## Design

- **One Chromium, in Cosmos's process.** `CosmosCEF` (Objective-C++) holds:
  - `CosmosApplication`, the `NSApplication` subclass CEF needs (`CefAppProtocol`).
  - `CosmosCEFReservePipe()`, which takes descriptors 3 and 4 for Chromium's DevTools pipe. It runs first in `main`, and in tests from `+load` as the test bundle loads, since a test process already has 4 to 11 open from its parent but uses neither 3 nor 4.
  - `CosmosCEFRuntime`, which starts CEF once, with an external message pump on the main queue.
  - `CosmosCEFContext`, one per profile.
  - `CosmosCEFBrowser`, a page drawn inside an `NSView` Cosmos owns.
- **Profiles are request contexts.** Cosmos's default profile is CEF's global context, whose folder is the first profile's own inside the engine's root (see below). That is the only profile extensions load into: `Extensions.loadUnpacked` uses DevTools' default browser context. Every other profile is a context of its own, and a private window's context keeps nothing on disk. Its downloads wait in `cosmos-private-<pid>-<uuid>/` in the temporary directory until Cosmos moves them; the folder goes 4 seconds after the window closes, and folders of Cosmoses that have ended (or of the older kind without a process number) are removed as Chromium starts (`PrivateFolderTests`).
- **Pages are found by target.** A browser asks its own DevTools channel (`ExecuteDevToolsMethod`, `Target.getTargetInfo`) for its target ID, so Cosmos knows exactly which page target each CEF browser is. Popups are made by CEF, inside a holding view, and are matched the same way.
- **Cosmos attaches to its own targets; Chromium does not auto-attach.** With `Target.setAutoAttach` on at the browser level, in any form (pages only, service workers only, with or without `waitForDebuggerOnStart`), a page's `window.open` never returns under CEF: its renderer stays blocked. So the runtime only discovers targets (`Target.setDiscoverTargets`) and attaches with `Target.attachToTarget`: a page when its browser says which target it is, an extension's service worker when it is created. A CEF browser's target is also `other` when it is made, not `page`, so a page filter would not have caught it anyway. What that costs:
  - Cosmos's own pages lose nothing: they start at `about:blank` and Cosmos loads the address only once its scripts are in.
  - A popup's first page runs before Cosmos is attached, so it has no page agent or Boosts, and no sign-in sheet (the site's own "sign in" page shows). The dangerous-site check does not depend on that: it comes from CEF's request handler (`OnBeforeBrowse`), which sees every navigation of every browser, the first one included. (CEF's `GetAuthCredentials` is never called here, so sign-in stays on `Fetch.authRequired`.) A permission the page asks for there gets what the profile holds for its site: what the user allowed or refused, once Cosmos has put that in during this run (it does as a page of the site opens), and a refusal otherwise. What Chromium kept from the last run is taken out of the profile's `Preferences` before it opens, so a decision the user took back while the site was closed is not left in place.
  - An extension's worker is attached after it starts, so Cosmos's script is in the extension's own files, ahead of its worker (see Extensions below); Cosmos counts a worker only once that script says it is ready, since Cosmos can be attached before the worker has run a line.
  - Set-up commands for a session go out in order, followed at once by `Runtime.runIfWaitingForDebugger`, with no waiting for answers in between: a frame Chromium holds for Cosmos answers nothing until it is let go.
- **One connection.** A single `CDPConnection` on the pipe carries everything. Page sessions go to their page, and browser-level events go to the profile of the target's `browserContextId`, or to the default profile. The page agent, isolated worlds, request interception and sign-in code stay as they are.
- **What a profile sets goes through CEF, not the protocol.** Browser-wide DevTools commands that name a browser context (`Browser.setPermission`, `Browser.setDownloadBehavior`, `Storage.clearCookies`) only find contexts DevTools made itself (`Target.createBrowserContext`), not CEF's. So each profile's permissions are CEF content settings (`CefRequestContext::SetContentSetting`), camera and microphone are granted by `OnRequestMediaAccessPermission` when the page's site has them, downloads go through CEF's download handler, cookies are deleted through the context's cookie manager, and settings are set as the profile runs (`CefPreferenceManager`). Commands sent on a page's own session (`Network.clearBrowserCache`, `Storage.clearDataForOrigin`) act on that page's profile.
- **Dialogs and menus.** A page's `alert`, `confirm`, `prompt` and leave-the-page question come to Cosmos through CEF's dialog handler, not `Page.javascriptDialogOpening` (CEF would show its own as well). CEF's context menu is emptied, so it shows none and Cosmos's own appears. A permission prompt CEF would otherwise leave unanswered for ever (the page waits) is answered from the profile's content settings, where Cosmos put the user's answer.
- **DevTools** open in a window CEF makes: asked to draw them in a view of Cosmos's, CEF stops ("Alloy style is not supported for this browser").
- **Blocking.** The blocker is an extension, and extensions load into the default profile only; a private window's in-memory profile is made from that one, and the blocker is loaded with `enableInIncognito`. Other profiles block on their own (see "Blocking in other profiles" below).
- **The default profile is chosen by ID.** CEF's global context is the first profile's (`workspace.profiles[0]`). Each profile's data is its own folder in `Engine Profiles/`, the root: Chromium opens a profile only when its folder is directly inside the root (otherwise it logs "Cannot create profile" and the page has no profile), so the headless Chromium's layout, with each profile in a `Default` folder of its own, is not kept.
- **What goes:** the snapshot installer, the per-profile processes, the screencast as the way pages are shown, input forwarding, drops, the cursor, caret and `<select>` relays, and the accessibility mirror. CEF's view does all of these natively. The screencast stays only for Picture in Picture, and runs only while a video is in it.
- **Zoom is Chromium's, by site**, as in Chrome: `EnginePage.zoom` reads and sets the zoom of the site the page shows.
- **Restart Engine** cannot restart a Chromium that runs inside Cosmos: it sets the current settings into the running profiles and reloads their pages. Turning the graphics processor off waits for the next launch.
- **Chromium's sandbox is on.** The helper (`Sources/CosmosHelper`) enters it first, with CEF's `libcef_sandbox.dylib`, then loads the framework: renderers, the GPU process, and the network and storage services run sandboxed, as in Chrome. The sandbox lets a helper read only the app the browser process is, so it works only when Cosmos.app is that process.
- **Closing a page does not close its window.** CEF closes a page by asking the window it is in to close (`performClose:`), all the other tabs with it, unless the client takes the page's own view out instead (`DoClose`), which Cosmos does.
- **Quitting waits for Chromium.** Cosmos answers the quit with "later", closes every page, and stops CEF (`CefShutdown`) once each has closed, so the cookies and settings Chromium keeps in memory for a while reach the disk; then it ends. A page that has not closed in three seconds leaves Chromium as it is, and Cosmos ends anyway.
- **Loading the framework.** Loading CEF's framework puts Chromium's memory allocator in place of the system's for the whole process, and a thread that frees memory while it does so can crash the process. Cosmos loads it first thing in `main` (`ChromiumEngine.prepareApplication`), before any other thread runs; it used to load it as Chromium started, while the filter lists were being read on another thread.
- **Quitting from a page.** ⌘Q while a page has the keyboard reaches the menus from inside CEF's work on the main thread (Chromium sends the key to the page first and hands it back unhandled). Waiting for Chromium to stop there would wait forever, so Cosmos calls that quit off and makes it again from the run loop (`CosmosCEFRuntime.isDoingWork`, `applicationShouldTerminate`).
- **The keyboard.** Cosmos gives a page the keyboard by making its view the first responder; the view hands it to CEF's (`SetFocus`).
- **Cookies for the session only** (no expiry date) end when Cosmos quits, as in Chrome when it opens a new window at launch.
- **Clearing data in profiles other than the default one.** Only the default profile has the bridge extension, which clears every site's storage and Chromium's history. Elsewhere, Chromium keeps no history (`history.saving_disabled`; Cosmos keeps the one people see), and Clear Site Data deletes every cookie, the cache and the storage of each site the profile has been on since Cosmos started, through a page of the profile that is never shown. Without Chromium's history there, a link's `:visited` colour does not show in those profiles. A site that stored something in an earlier run and has not been opened since keeps it: Chromium cannot list the sites that have storage. The confirmation says so.
- **Extensions.** Cosmos's pages are not Chrome tabs, so `chrome.tabs` finds none and `Extensions.triggerAction` has no tab to click in. Cosmos loads each extension from a copy (`ExtensionStage`, an APFS clone in `Cosmos Extensions/` of the default profile's folder) with its own scripts ahead of the extension's: the worker Chromium starts imports Cosmos's first (`extension-shim.js`), each set of content scripts starts with `extension-content.js`, and each page with the worker's script. Through them Cosmos answers `chrome.tabs`, `chrome.windows` and `chrome.scripting` by tab ids of its own, within Chrome's permission rules, delivers `tabs.sendMessage` into the extension's world in the tab's frames, tells a content script which tab it is in (from outside the page, which cannot reach that world), and fires the toolbar button, menu items and shortcuts itself. A popup is the extension's page, opened by Cosmos. The worker's script answers nothing until Cosmos is attached and holds what it says until then. Loading an extension when Chromium is not running yet loads it once: starting Chromium loads every extension, and a second load would replace the worker it had just started. Chromium refuses an extension with a file whose name starts with "_", so Cosmos's are in `cosmos-extension/`. A sign-in (`launchWebAuthFlow`) ends at the extension's `chromiumapp.org` address before any request goes there.
- **Blocking in other profiles.** Only the default profile (and a private window, made from it) has the blocker extension; every other profile matches requests against the same rules itself (`RequestRules`, asked by CEF's resource handler on the network thread, before the request leaves) and hides with a page script.
- **Downloads Cosmos starts** ("Download Linked File", "Download Image") go through CEF (`StartDownload`), with the page's profile and cookies, so a file from another site downloads instead of replacing the page.
- **What Chromium reaches by itself.** Measured on 2026-10-30 with Chromium's network log (`--log-net-log`, added for the run only) on a new profile, idle for 100–150 seconds and then on one page: Chromium's component updater (`update.googleapis.com`, and its downloads from `edgedl.me.gvt1.com`), Safe Browsing list updates (`safebrowsing.googleapis.com`), a clock check (`clients2.google.com/time`), the address bar's AI Mode eligibility check (`www.google.com/async/folae`, and a policy report its answer asks for to `csp.withgoogle.com`). Cosmos turns off what it has no use for: Safe Browsing (`safebrowsing.enabled`; Cosmos warns from lists of its own), and the features `NetworkTimeServiceQuerying` (used by Chrome's certificate error pages, which Cosmos does not show), `AimServerEligibilityEnabled`, `AimServerRequestOnStartupEnabled` and `OptimizationHints` (Chrome's page hints, which ask about the sites you visit; not seen in the run, off anyway) (`ChromiumPreferences`). Measured again with those off: only the component updater and the page. The component updater stays: it brings certificate revocation lists and Certificate Transparency logs (without fresh ones Chromium stops enforcing Certificate Transparency), download file-type rules and SSL error data, together with components Cosmos does not use (optimization hints, on-device suggestions, privacy sandbox attestations, …), and it sends Google only Chromium's version and its components' versions. No metrics were sent.
- **The Keychain item.** Chromium keeps the key it encrypts cookies with in the Keychain, as "Chromium Safe Storage", the name any Chromium build uses; an ad hoc signed Cosmos is asked about it again after each rebuild.
- **Tests** start CEF once per test process (`CEFTestRuntime`) and share it. The helper apps go inside a stand-in app, because helpers find the browser by the bundle identifier of the app they sit in; the framework is a copy there (an APFS clone), not a link. The test process is not that app, so its helpers run without the sandbox. What only a process of its own can show (the sandbox, quitting, Chromium's history) is checked with `CosmosEngineCheck`, which the tests put inside an app of its own, with the helpers, and run: it shows a page in a window that is never on screen, reports Chromium's processes and quits as Cosmos does. Tests use `--use-mock-keychain`; the app uses the real Keychain. Test pages are in views that are in no window, or in a window that is never shown.

## Order of the work

All five steps are done.

1. `scripts/fetch-cef.sh` downloads and checks the pinned CEF build into `Vendor/CEF/` (git-ignored). A SwiftPM C++ target builds CEF's wrapper from it, and an Objective-C++ target holds the CEF client and the `CefAppProtocol` application class.
2. CEF starts in Cosmos's process with an external message pump on the main run loop. The DevTools pipe is set up before `CefInitialize`. The live tests run against it.
3. An engine conformance on CEF: pages as CEF browsers in `NSView`s, found as targets over the pipe and driven by the existing protocol code. The screencast, input forwarding and accessibility mirror go.
4. Extensions: the tabs API and the toolbar button answered by Cosmos, Cosmos's scripts in a copy of each extension ahead of its own, and blocking for profiles other than the default one.
5. `scripts/build-app.sh` puts the framework and the five helper apps (`Cosmos Helper`, `(Alerts)`, `(GPU)`, `(Plugin)`, `(Renderer)`) into the bundle. The snapshot installer goes.
